### 破案 9/1 晚 pipeline push 失败根因
- 不是 push 失败，是 **`git commit` 超时 120s**（TimeoutExpired 杀进程）
- commit 对象实际已写完（本地有 f526fd082），但后续 pull/push 没执行
- 根因：launchd `ProcessType=Background` 调度优先级把 git 拖慢 10~30 倍（手动 4s 的 commit 在 launchd 下 120s+）

### 修复（双管齐下）
1. pipeline.py step_backup 所有 git timeout 统一放大：status 10→60s，commit 120→600s（加 returncode 检查），pull 120→300s，push 180→600s
2. launchd plist `ProcessType: Background → Utility`（更高调度优先级），unload/load 重载生效

## 早上：GitHub 大小治理调查 + 双仓架构决策

### 测量结果（2026-09-02 08:00）
- GitHub 端 repo size ~1.9GB；本地 .git 1.5GB；tracked 工作树 4.54GB（daily/ 12461 文件为主）
- 单日 commit 5590 文件 / ~19 万行变化；其中 a_shares Q3 包纯追加（+5575 行），**etf/hk Q3 包每天全文件重写（~18 万行全变）**
- 根因：export_daily 仅 `ORDER BY trade_date`，同日内行序由 PG 堆表顺序决定，update/vacuum 扰动 → 行序 shuffle → git 全文件重写
- bare 仓 gc 实验：基线 1442.7MB → +1 日增量 gc 后 1430.9MB（delta 压缩有效，真实存储成本极低；之前测的 293MB 是胖包伪影）
- 结论：GitHub 无总量硬限制，真正限制是单文件 100MB（当前最大 36MB data/daily/a_shares/2025-Q3.csv，安全）

### 修复
- scripts/export.py export_daily 加二级排序键 `ORDER BY {ts_col}, "{cols[0]}"`（commit 056bbc0d5）→ 每日恢复纯追加，增量降到 MB 级

### 双仓架构（用户决策）
- 用户拍板：历史仓（冻结）+ live 仓（增量），所有数据都要在 GitHub
- 设计：旧仓 en574894764/stock_data 直接冻结当历史仓（零迁移）；新建 stock_data_live = 完整当前快照 + 每日增量（不是纯 delta，保证单仓自包含）
- GitHub MCP token 无建仓权限（403），HTTPS credential 无存储（用 SSH push）→ 需用户手动在 GitHub 建 stock_data_live
- 切换步骤（等 hk_catchup 完成后）：验证 PG → 全量重导（Q3 包新排序一次性重写）→ 推旧仓（冻结点）→ mv .git 出去当本地归档 → git init 快照 → push live 仓（~1.4GB 一次性）
- 注意：旧仓是 public 的；live 仓计划 private
