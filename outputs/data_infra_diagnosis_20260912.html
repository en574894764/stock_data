四、发现的问题与修复方案

P1 退市股历史行情缺口（约 1600 只，2016 年→退市日）

证据：

  • 000005.SZ ST星源(退)：真实退市日 2024-04-26，但 PG 日线止于 2015-12-31 → 缺 8.3 年
  • 000018.SZ 神城A退：退市 2020-01-07，数据止于 2015-12-31 → 缺 4 年
  • 002781.SZ 奇信退：2015 上市、2023 退市，PG 仅 8 行日线
  • L1 报告：「已退市但数据未到退市日 273 只」+ freshness「往年 375 只」+ CSV 落后文件 1631 个（差额 1100~1342 行/只 ≈ 5 年交易日数，口径吻合）

影响：退市股在退市前最后几年的行情缺失 → 回测时这些股票在缺失区间的收益不可计算，产生幸存者偏差（对因子/组合回测的尾部风险低估）。

背景：2026-09-12 上午手动回补了 2010-2015 段（≈25-30 万行，1631 个文件差即源于此，且因此 CSV 曾落后 PG —— 已重导对齐）。但 2016→退市日区间仍未补。

修复方案（一次性 backfill_delisted.py）：

  1. 从 stocks 取 delist_date IS NOT NULL 全部标的，联 daily_quote MAX(trade_date) 算出缺口区间 [MAX+1, delist_date]；
  2. tushare pro_bar 对退市股可用（含已摘牌），按区间逐只拉取 → 复用现有 staging + ON CONFLICT upsert 写入；tushare 拉不到的用 akshare 东财港股/A股接口兜底；
  3. 分批跑（每批 100 只，断点续传：跑前先查 PG MAX），预计 1600 只 × 平均 4 年 ≈ 160 万行；
  4. 跑完执行 scripts/export.py 重导 CSV + validate.py 验证「已退市但数据未到退市日」应降到个位数；
  5. 财报同理：把退市股纳入 backfill_financial.py 的回补范围（当前 2010-2025 有 43,651 个 (股,年) 财报组合不足 4 份，其中大量是退市股）。

已修复 本轮诊断中发现并已处理的两项

  • CSV 落后 PG 1631 个文件（今天上午手动改 PG 后未重导）→ 已跑 scripts/export.py 重导，reconcile 复核 PG↔CSV 行数全一致、抽样内容比对全一致。⚠️ 注意：这批更新的 CSV 尚未 git commit，下个交易日 pipeline 会自动提交；防复发规则：今后绕过 pipeline 动 PG 后必须跑 scripts/export.py。

五、validate.py 优化方案

先说结论：脚本结构清晰、检查维度设计合理（制度感知的涨跌停、源特性豁免、missing-report 闭环都做得很好），有优化空间但不是重写。分三块：性能、覆盖缺口（重点）、可运维性。

A. 覆盖缺口（最有价值，建议优先做）

#缺口现状问题优化方案
1中间断档无感知check_daily_per_stock 只看首/末日期。若某股 2018-03~2018-09 整段缺失，首末都正常，完全检测不到。本次手动回补的 2010-2015 数据质量也无法用现有质检验证。新增 check_gap()：per-symbol JOIN trade_cal 找工作日缺口（generate_series 或 trade_cal - daily_quote 反连接）。全量跑重，可只对 2015+ 或 top 市值标的做，或者作为 --deep 模式周度跑。
2trade_year 分区键一致性daily_quote 按年分表，若写入时 trade_year 算错，同一 (ts_code, trade_date) 会跨分区出现逻辑重复，现有检查发现不了。加一条轻量检查：SELECT COUNT(*) FROM daily_quote WHERE EXTRACT(YEAR FROM trade_date)::int <> trade_year（可走索引，秒级）。应为 0。
3PG↔CSV 对账只在周六本轮"手动改 PG 忘重导 CSV"正是靠周六 L2 才发现；若发生在周日，要滞后近一周。L1 每日加抽样 50 文件行数对账（PG count vs CSV 行数），秒级完成；L2 保留全量。
4ETF/指数无逐标检查etf_quote / index_daily 只查全表 MAX(trade_date)，单只 ETF 断更发现不了。逐标连续性检查扩展到两表（逻辑与 daily_quote 相同，可用同一函数参数化）。
5expected_start 形同虚设参数接了但 check_table_ranges 从不比较 MIN(date)，覆盖起点不足不会告警。补一条：MIN(trade_date) > expected_start-01-01 时 WARN「覆盖起点晚于预期」。
6财报检查粒度cashflow「653 只缺整年」混在一起，早年源特性与真实缺失不分。缺整年明细按年份分布输出；2010+ 且缺整年的优先级高于早年。

B. 性能（89.7s → 预计 ~35s）

#现状方案
7check_daily_per_stock（全表 GROUP BY MIN/MAX/COUNT）与 check_daily_freshness（又一次全表 GROUP BY MAX）— 同样的全表聚合跑了两遍，占耗时大头合并为一条 CTE：WITH agg AS (SELECT ts_code, MIN, MAX, COUNT FROM daily_quote GROUP BY 1)，逐标连续性和新鲜度分布共用一次聚合，省约 30-40s。
8check_ohlc_quality 三条独立全表扫（负价 / high<low / NULL）合并为一条 SUM(CASE...) 单扫。
9pct_chg 自洽检查全表扫描，但 2015 前只是"统计记录"2015+ 走分区裁剪主查；2015 前降频为周度或干脆并入 L2。
108619 标的逐行 Python 循环分档改 SQL CASE 聚合（次要，Python 循环 8k 行本身不慢，顺手即可）。

C. 可运维性

#建议
11校验结果历史化：每次运行 append 一行摘要到 logs/validate_history.jsonl（时间、errs/warns/stale 数）。趋势可见后，"stale 周环比"这类退化能在告警前肉眼发现，也能自动回答"上次全绿是什么时候"。
12L3 cross_validate 自动化：加进 pipeline 周五收盘后（或交易日 18:30 尾部），腾讯快照接口当前实测可用；同时把本次诊断的"历史锚点"模式（新浪不复权 K 线抽样）做成 --anchor 选项，月度跑一次覆盖 2015/2018/2020/2023 等锚点。东财接口限流严重（本轮多轮 SKIP 的原因），建议 L3 自动化用腾讯/新浪，不要依赖东财。
13freshness「往年 375 只」自动对照 stocks.delist_date 细分为「退市股/异常滞留」，ERR 数会随 P1 修复下降，趋势更干净。
14财报金额 sanity（利润表 total_revenue ≤ 0 行计数、净利润 NULL 计数）——与 L2 的净利率 flag 呼应。
